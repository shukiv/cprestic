# Gniza v0.2.0

Release channel: stable

cP:Restic is now Gniza — Backup. Restore. Repeat. The program, the service,
the directories and the WHM plugin all change name in this release. Nothing
about how backups are taken, stored or restored changes with it.

## Changes

- The service is `gniza`, the binaries are `gniza-agent` and `gniza-hook`,
  and the WHM plugin is listed as **Gniza Backups**.
- The directories move: `/etc/cprest` to `/etc/gniza`, `/var/lib/cprest` to
  `/var/lib/gniza`, `/var/cache/cprest` to `/var/cache/gniza`, and
  `/var/run/cprest` to `/run/gniza`. The installer moves them; the agent
  rewrites the paths recorded inside the state file to match, including the
  SSH key and known-hosts file every SFTP destination connects with.
- The plugin's Feature Manager feature is now named `gniza`.
- The sidebar mark and the logo are Gniza's.

## Upgrade notes

- Upgrading from a cP:Restic release is a one-way move. The installer stops
  and unregisters the old installation before it moves anything, and it
  refuses to start if both the old and the new directory already exist
  rather than guess which one is current. The master key and the state file
  are carried across, not regenerated: existing repositories, destinations
  and schedules keep working.
- Back up `/etc/cprest` and `/var/lib/cprest` before upgrading. The keys
  under `/etc/cprest/keys` are what reach the backup server, and they are
  not recoverable from anywhere else.
- Check Feature Manager after upgrading. A feature list that named the old
  plugin explicitly has to be given `gniza` before customers see the page
  again. A list that never named it is unaffected.
- The published tarball keeps its old asset name, and so does the word at
  the top of `SHA256SUMS`. Servers running a cP:Restic release ask for those
  spellings by name, and renaming them would leave those servers unable to
  install this release at all.
- Bug reports still go to program `cprestic` at the intake service. The
  intake registration is a separate system and was not renamed; the key
  file moves with the config directory to `/etc/gniza/bugs-intake.key`.

## Validation boundary

Passed for this version: the full Go test suite, the end-to-end
backup/restore tests, `make vet` including the end-to-end build tag, `gofmt`,
and a check that the three identifiers deployed servers depend on are
unchanged.

The restore compatibility limits documented for v0.1.6 still apply and are
unchanged by this release.
