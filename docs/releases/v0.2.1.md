# Gniza v0.2.1

Release channel: stable

Fixes the upgrade from cP:Restic, which v0.2.0 could not complete.

## Changes

- The installer carries the package with it when it renames the
  directories. A self-upgrade unpacks the release under the state
  directory and runs it from there, so moving `/var/lib/cprest` to
  `/var/lib/gniza` moved the installer's own files while it was running.
  Everything after that point looked for them at the old path and did not
  find them.
- If the package is still not where the installer expects after the move,
  it now says so in those words. The old installation is gone by then, so
  a missing file is a server with no backups on it and the message has to
  explain that rather than name one file.

## Upgrading from v0.2.0

Nothing to do. v0.2.0 is only reachable by a server that already completed
the rename, and this changes nothing that runs on one.

## Upgrading from a cP:Restic release

Use this release, not v0.2.0.

A server left half-migrated by v0.2.0 — the old installation removed, no
service running, `/etc/gniza` and `/var/lib/gniza` in place — is finished by
running the installer again from where the package now is:

```sh
sh /var/lib/gniza/upgrade/v0.2.0/cprest-plugin/install.sh
```

Nothing is lost in that state: the master key, the state file and the
destination keys were moved, not removed, before the failure.

## Validation boundary

The failure is covered by a test that runs the installer's own move loop
against a package inside the directory being moved, so the case that broke
a live server is now the case the test asserts.
