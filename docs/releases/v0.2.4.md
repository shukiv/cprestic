# Gniza v0.2.4

Release channel: stable

`debug` now has something to say, and a failed database dump says what went
wrong rather than only that it did.

## Changes

- **A failed `mysqldump` reports what mysqldump said.** Its standard error
  was being discarded, so a backup failed with `cpanel: mysqldump db: exit
  status 2` and finding out why meant running the same command by hand on
  the server. The last lines of the complaint are now part of the failure,
  where they were all along — `Lost connection to MySQL server during
  query (2013)`, for instance, which is a corrupt table and not a Gniza
  problem at all.
- **`debug` writes down what was run.** Every `pkgacct`, `mysqldump` and
  `restic` invocation with its arguments and how long it took; which
  schedule was due and which was not and why; which accounts a schedule
  resolved to, by name; each destination probe; the staging and the upload
  of each account, with the snapshot each copy produced. A failure can be
  reproduced by hand from the log. The `pkgacct` and `mysqldump` lines
  carry the account, so the Logs page's account filter keeps them; the
  `restic` lines do not, because that runner works on repositories and is
  told nothing about whose account it is copying.

## What is never logged

The service log is readable in the interface and downloadable from it, so
what goes into it is chosen rather than swept up. At no level does it carry
restic's environment — where the backend credentials and the repository
password file's path are — nor the value of any `-o` backend option, whose
key is kept and whose value is not, nor a login embedded in a repository
address, which becomes `[credentials]`. A test fails if any of those reach
a log line.

Every line added here is at `debug`, so a server at the default level
writes exactly what it wrote before.
